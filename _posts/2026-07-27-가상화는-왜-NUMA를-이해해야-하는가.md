# 가상화는 왜 NUMA를 이해해야 하는가

## Intel·AMD 하드웨어에서 QEMU/KVM, vNUMA, AWS Nitro, Kubernetes까지

가상화는 물리 서버의 CPU와 메모리를 추상화한다.

사용자는 VM에 8 vCPU, 32GB RAM을 할당하면서 해당 CPU가 어느 소켓에 있고 메모리가 어느 메모리 컨트롤러에 연결됐는지 신경 쓰지 않아도 된다. 이것이 가상화가 제공하는 가장 큰 편의성이다.

하지만 추상화는 물리적 거리를 없애지 않는다.

VM에 보이는 32GB 메모리도 결국 물리 서버의 어느 DIMM에 저장되어야 한다. vCPU 역시 어느 물리 코어에서 실행되어야 한다. vCPU가 실행되는 코어와 메모리가 서로 다른 NUMA 노드에 있다면, 메모리 접근은 CPU 간 인터커넥트를 통과해야 한다.

따라서 NUMA와 가상화의 관계는 다음 문장으로 요약할 수 있다.

> 하이퍼바이저는 하드웨어 토폴로지를 숨길 수 있지만, 그 토폴로지가 만드는 성능 차이까지 제거할 수는 없다.

이 글에서는 NUMA가 등장한 배경부터 Intel과 AMD 서버의 구조, QEMU/KVM의 메모리 매핑, vNUMA, AWS Nitro와 Kubernetes까지 기술 흐름을 연결해서 살펴본다.

---

# 1. CPU가 빨라질수록 메모리는 더 멀어졌다

초기의 대칭형 다중 처리 시스템, 즉 SMP 시스템에서는 여러 CPU가 하나의 메모리 버스와 메모리를 공유했다.

```
CPU 0 ─┐
CPU 1 ─┼── Shared Memory Bus ── Memory
CPU 2 ─┤
CPU 3 ─┘
```

이 구조에서는 모든 CPU가 동일한 메모리를 거의 같은 비용으로 접근한다. 이러한 구조를 일반적으로 UMA, 즉 Uniform Memory Access라고 부른다.

문제는 CPU 수가 증가하면서 시작된다.

모든 CPU가 하나의 메모리 버스와 메모리 컨트롤러를 공유하면 다음 문제가 발생한다.

- 메모리 버스 경합

- 메모리 대역폭 부족

- 캐시 일관성 유지 비용 증가

- CPU 증가에 비해 확장되지 않는 메모리 성능

이를 해결하기 위해 각 CPU 소켓에 메모리 컨트롤러와 메모리를 배치하는 구조가 등장했다.

```
┌──────────────── NUMA Node 0 ────────────────┐
│ CPU Socket 0 ─ Memory Controller 0 ─ DRAM 0 │
└───────────────────┬─────────────────────────┘
                    │ UPI / Infinity Fabric
┌───────────────────┴─────────────────────────┐
│ CPU Socket 1 ─ Memory Controller 1 ─ DRAM 1 │
└──────────────── NUMA Node 1 ────────────────┘
```

CPU 0이 DRAM 0을 접근하면 로컬 메모리 접근이다. 반대로 CPU 0이 DRAM 1을 접근하려면 소켓 간 인터커넥트와 다른 소켓의 메모리 컨트롤러를 통과해야 한다.

이것이 원격 메모리 접근이다.

Intel은 다중 소켓 시스템에서 로컬 메모리가 원격 메모리보다 일반적으로 더 좋은 지연 시간과 대역폭을 제공하며, 원격 접근은 소켓 간 UPI 트래픽을 발생시킨다고 설명한다.

NUMA에서 Non-Uniform이라는 표현은 어떤 메모리는 접근할 수 있고 어떤 메모리는 접근할 수 없다는 뜻이 아니다.

모든 프로세서는 전체 메모리를 접근할 수 있지만, CPU와 메모리의 상대적인 위치에 따라 비용이 달라진다는 의미다.

# 2. Intel과 AMD는 NUMA를 어떻게 구성하는가

## 2.1 Intel Xeon: 메모리 컨트롤러와 UPI

현대 Intel Xeon 다중 소켓 서버에서 각 프로세서 소켓은 자체 코어, 캐시, 메모리 컨트롤러와 연결된 메모리를 가진다.

다른 소켓에 연결된 메모리를 접근해야 할 때는 UPI, 즉 Ultra Path Interconnect를 통과한다.

```
Core
  │
Cache
  │
Socket 0 Memory Controller ── Local DRAM
  │
 UPI
  │
Socket 1 Memory Controller ── Remote DRAM
```

따라서 성능 분석에서는 단순히 메모리 사용량만 확인해서는 안 된다.

- 어느 소켓의 코어에서 스레드가 실행됐는가

- 메모리 페이지가 어느 NUMA 노드에 생성됐는가

- 소켓 간 UPI 트래픽이 얼마나 발생하는가

- 스레드가 실행 도중 다른 소켓으로 이동했는가

이 항목을 함께 봐야 한다.

Intel VTune의 NUMA 분석 예제에서도 스레드 affinity가 설정되지 않으면 운영체제가 스레드를 서로 다른 소켓으로 이동시킬 수 있고, 그 결과 원격 메모리 접근과 소켓 간 트래픽이 증가할 수 있다고 설명한다.

---

## 2.2 AMD EPYC: CCD, IOD와 Infinity Fabric

AMD EPYC는 칩렛 기반 구조를 사용한다.

대표적인 EPYC 구조는 여러 개의 CCD, 즉 Core Complex Die가 중앙의 IOD, 즉 I/O Die 주변에 배치되는 형태다.

```
       CCD      CCD
         \      /
          \    /
          ┌───────┐
CCD ───── │  IOD  │ ───── CCD
          └───────┘
          /   │   \
       Memory I/O  Memory
```

CCD에는 CPU 코어와 캐시가 존재하고, IOD에는 메모리 컨트롤러, PCIe와 각종 I/O 연결이 포함된다. CCD와 IOD 사이의 통신에는 AMD Infinity Fabric이 사용된다.

AMD 문서에서는 Infinity Fabric이 CCD와 메모리, I/O를 연결하고 각 CCD가 전용 GMI 링크를 통해 IOD에 연결된다고 설명한다.

> 그림 2. AMD EPYC의 CCD·IOD 칩렛 구조

AMD EPYC 9004 아키텍처 공식 그림 열기

AMD EPYC에서 중요한 설정이 NPS, NUMA Nodes Per Socket이다.

예를 들어 NPS1은 소켓 전체를 하나의 NUMA 노드로 보여준다. NPS2는 한 소켓을 두 NUMA 노드로, NPS4는 네 개의 NUMA 노드로 나눈다.

```
NPS1
Socket 0 = NUMA Node 0

NPS2
Socket 0 = NUMA Node 0 + NUMA Node 1

NPS4
Socket 0 = NUMA Node 0 + 1 + 2 + 3
```

NPS 값을 높이면 더 세밀한 메모리 locality를 표현할 수 있지만, NUMA 노드당 사용할 수 있는 메모리 채널과 자원 배치도 달라진다. 따라서 무조건 NUMA 노드 수를 많이 만드는 것이 좋은 것이 아니라 워크로드의 병렬성, 메모리 대역폭과 locality 특성을 함께 고려해야 한다. AMD도 NPS 설정을 로컬 메모리 지연을 줄이는 방향과 메모리 대역폭을 활용하는 방향 사이의 선택으로 설명한다.

# 3. 가상화가 들어오면 토폴로지가 두 개가 된다

물리 서버에서 애플리케이션을 직접 실행한다면 운영체제는 ACPI 정보를 통해 물리 NUMA 토폴로지를 파악할 수 있다.

그러나 VM이 들어오면 NUMA 토폴로지가 두 계층으로 나뉜다.

```
Guest OS가 보는 토폴로지
┌─────────────────────────────┐
│ vNUMA 0       vNUMA 1       │
│ vCPU + vRAM   vCPU + vRAM   │
└──────────────┬──────────────┘
               │ Hypervisor mapping
┌──────────────┴──────────────┐
│ pNUMA 0       pNUMA 1       │
│ pCPU + DRAM   pCPU + DRAM   │
└─────────────────────────────┘
Host가 실제로 가진 토폴로지
```

여기서 구분해야 할 용어는 다음과 같다.

- pNUMA: 물리 서버의 실제 NUMA 구조

- vNUMA: 하이퍼바이저가 게스트 운영체제에 보여주는 가상 NUMA 구조

가상화 환경의 성능은 단순히 vNUMA 구조만 올바르다고 해결되지 않는다.

다음 두 조건이 동시에 만족되어야 한다.

1. 게스트의 vCPU와 가상 메모리가 올바른 vNUMA 노드로 구성되어야 한다.

1. 해당 vNUMA 노드가 호스트의 동일한 pNUMA 노드에 가깝게 매핑되어야 한다.

즉, 게스트 내부의 토폴로지와 호스트의 실제 배치가 일치해야 한다.

# 4. QEMU와 KVM은 각각 무엇을 담당하는가

QEMU와 KVM은 자주 하나의 기술처럼 표현되지만 역할이 다르다.

QEMU는 게스트가 사용할 가상 머신 모델을 만든다.

- vCPU 토폴로지

- 가상 메모리

- 칩셋

- 디스크 컨트롤러

- 네트워크 장치

- PCI 장치

- 펌웨어와 ACPI 테이블

QEMU 공식 문서는 시스템 에뮬레이션 모드에서 CPU, 메모리와 에뮬레이션 장치로 구성된 전체 가상 머신 모델을 제공하고, KVM과 같은 하이퍼바이저를 accelerator로 사용할 수 있다고 설명한다.

KVM은 Linux 커널 내부에서 하드웨어 가상화를 제공한다.

QEMU는 /dev/kvm을 열고 ioctl을 호출해 VM과 vCPU를 생성한다.

```
QEMU userspace
    │
    ├── open("/dev/kvm")
    ├── KVM_CREATE_VM
    ├── KVM_CREATE_VCPU
    └── KVM_RUN
           │
           ▼
Linux KVM
           │
           ▼
Intel VT-x / AMD-V
```

Linux KVM API 문서에 따르면 /dev/kvm을 연 뒤 KVM_CREATE_VM으로 VM 파일 디스크립터를 만들고, VM 파일 디스크립터를 통해 vCPU와 장치를 생성한다. KVM_RUN ioctl은 해당 게스트 vCPU를 실행한다.

> 그림 3. QEMU와 KVM의 실행 구조

QEMU 공식 Architecture 그림 열기

따라서 "KVM이 모든 VM을 만든다"라는 설명은 충분하지 않다.

보다 정확하게 표현하면 다음과 같다.

> QEMU가 가상 머신의 사용자 공간 모델과 장치를 구성하고, KVM이 게스트 CPU 실행을 하드웨어 가상화 기능으로 가속한다.

# 5. Guest RAM은 결국 QEMU 프로세스의 메모리다

게스트 운영체제는 자신이 물리 메모리를 사용하는 것처럼 생각한다.

```
Guest Virtual Address
        ↓
Guest Physical Address
        ↓
Host Virtual Address
        ↓
Host Physical Address
        ↓
Physical NUMA Node
```

하지만 호스트 관점에서 VM의 메모리는 QEMU 프로세스에 매핑된 메모리 영역이다.

결국 Linux 호스트의 메모리 정책과 페이지 할당 결과에 따라 QEMU 메모리 페이지가 특정 NUMA 노드에 생성된다.

Linux의 기본 NUMA 메모리 정책은 일반적으로 페이지를 할당하는 CPU가 속한 노드에 가까운 로컬 할당을 우선한다. 또한 Linux는 preferred, interleave와 같은 NUMA 메모리 정책을 제공한다.

문제는 VM 부팅 시점에 메모리 페이지가 생성된 노드와 이후 vCPU가 실행되는 노드가 달라질 수 있다는 것이다.

예를 들어 다음과 같은 상태를 생각해보자.

```
vCPU 0~7
  ↓
Host NUMA Node 1에서 실행

Guest RAM
  ↓
Host NUMA Node 0에 대부분 할당
```

이 경우 게스트 입장에서는 자기 메모리를 정상적으로 접근할 뿐이지만, 실제 하드웨어에서는 거의 모든 메모리 접근이 원격 접근이 될 수 있다.

가상화 환경에서 NUMA 문제가 눈에 잘 띄지 않는 이유가 여기에 있다.

게스트 내부에서는 특별한 오류가 발생하지 않는다. 애플리케이션도 정상 실행된다. 다만 지연 시간이 증가하고 처리량이 떨어지며 소켓 간 트래픽이 많아진다.

# 6. vNUMA는 왜 필요한가

작은 VM이 하나의 물리 NUMA 노드 안에 들어간다면 구조가 비교적 단순하다.

```
VM: 8 vCPU, 16GB RAM
          ↓
pNUMA Node 0
16 Core, 64GB RAM
```

하이퍼바이저가 vCPU와 메모리를 하나의 pNUMA 노드에 배치하면 게스트가 NUMA 구조를 몰라도 큰 문제가 발생하지 않을 수 있다.

하지만 VM이 한 물리 NUMA 노드보다 커지면 상황이 달라진다.

```
Host
pNUMA 0: 16 Core, 64GB
pNUMA 1: 16 Core, 64GB

VM
24 vCPU, 96GB
```

이 VM은 하나의 물리 NUMA 노드에 들어갈 수 없다. 두 노드의 CPU와 메모리를 함께 사용해야 한다.

이때 게스트에게 하나의 거대한 UMA 머신처럼 보이게 하면 게스트 운영체제는 CPU와 메모리 사이의 거리를 알 수 없다.

```
Guest가 잘못 이해한 구조

24 vCPU ───────── 96GB RAM
모든 메모리의 비용이 같다고 판단
```

vNUMA를 제공하면 게스트는 다음과 같이 인식할 수 있다.

```
Guest vNUMA 0
vCPU 0~11 + 48GB

Guest vNUMA 1
vCPU 12~23 + 48GB
```

게스트 Linux와 NUMA-aware 애플리케이션은 이 정보를 기반으로 스레드와 메모리를 가까운 노드에 배치할 수 있다.

VMware vSphere도 게스트 운영체제에 가상 NUMA 토폴로지를 노출하면 게스트 OS와 애플리케이션이 NUMA 최적화를 수행하기 쉬워진다고 설명한다.

> VMware 공식 참고 자료

vSphere의 Virtual NUMA 설명 열기

중요한 점은 vNUMA가 원격 접근을 제거하는 기능이 아니라 게스트가 거리 정보를 인식하도록 만드는 기능이라는 것이다.

실제 배치가 잘못되어 있다면 vNUMA만 노출해도 문제가 해결되지 않는다.

# 7. QEMU에서 vNUMA와 물리 메모리 배치를 구성하는 방법

QEMU는 -numa 옵션으로 게스트가 볼 NUMA 노드, vCPU와 메모리 구성을 정의할 수 있다.

QEMU 공식 문서에서 제공하는 주요 옵션은 다음과 같다.

```
-numa node
-numa cpu
-numa dist
```

- numa node는 NUMA 노드에 vCPU와 RAM을 연결한다. numa dist는 게스트가 인식할 NUMA 노드 사이의 거리를 설정한다. QEMU는 메모리 backend를 memdev로 NUMA 노드에 연결하는 방식을 권장한다.

다음은 두 개의 vNUMA 노드를 구성하는 개념적인 예제다.

```
qemu-system-x86_64 \
  -enable-kvm \
  -cpu host \
  -smp 16,sockets=2,cores=8,threads=1 \
  -m 32G \
  -object memory-backend-ram,id=mem0,size=16G,host-nodes=0,policy=bind \
  -object memory-backend-ram,id=mem1,size=16G,host-nodes=1,policy=bind \
  -numa node,nodeid=0,cpus=0-7,memdev=mem0 \
  -numa node,nodeid=1,cpus=8-15,memdev=mem1
```

이 설정은 두 가지 작업을 수행한다.

첫 번째는 게스트 토폴로지 구성이다.

```
vNUMA 0 = vCPU 0~7 + 16GB
vNUMA 1 = vCPU 8~15 + 16GB
```

두 번째는 호스트 메모리 배치 제약이다.

```
mem0 → Host NUMA Node 0
mem1 → Host NUMA Node 1
```

QEMU의 host-nodes 옵션은 메모리 영역을 지정한 호스트 NUMA 노드에 연결한다. policy=bind는 메모리 할당을 지정된 노드 집합으로 제한한다. preferred는 해당 노드를 우선하고, interleave는 여러 노드에 페이지를 분산한다.

다만 메모리만 bind한다고 끝나는 것은 아니다.

vCPU 스레드도 대응하는 호스트 CPU에 pinning해야 한다.

```
Guest vCPU 0~7
      ↓
Host NUMA 0의 물리 CPU

Guest vCPU 8~15
      ↓
Host NUMA 1의 물리 CPU
```

그렇지 않으면 메모리는 Node 0에 고정했지만 vCPU가 Node 1에서 실행되는 역효과가 발생할 수 있다.

---

# 8. libvirt에서는 <cpu>와 <numatune>을 구분해야 한다

실제 KVM 운영 환경에서는 QEMU 명령을 직접 작성하기보다 libvirt XML을 사용하는 경우가 많다.

libvirt에서는 두 설정을 구분해야 한다.

## 게스트에 노출할 vNUMA

```
<cpu mode="host-passthrough">
  <numa>
    <cell id="0" cpus="0-7" memory="16" unit="GiB"/>
    <cell id="1" cpus="8-15" memory="16" unit="GiB"/>
  </numa>
</cpu>
```

이 설정은 게스트가 보는 NUMA 토폴로지를 정의한다.

## 호스트 물리 NUMA 메모리 정책

```
<numatune>
  <memory mode="strict" nodeset="0-1"/>
  <memnode cellid="0" mode="strict" nodeset="0"/>
  <memnode cellid="1" mode="strict" nodeset="1"/>
</numatune>
```

cellid="0"인 게스트 NUMA 노드의 메모리를 호스트 NUMA Node 0에, cellid="1"의 메모리를 Host Node 1에 배치한다.

libvirt의 numatune은 QEMU 드라이버에서 도메인 프로세스의 NUMA 메모리 정책을 제어하며, memnode를 통해 각 게스트 NUMA 노드별 메모리 정책을 지정할 수 있다.

그리고 vCPU pinning을 함께 구성해야 한다.

```
<cputune>
  <vcpupin vcpu="0" cpuset="0"/>
  <vcpupin vcpu="1" cpuset="1"/>
  <!-- 생략 -->
</cputune>
```

핵심은 다음 세 구성을 하나의 세트로 보는 것이다.

```
Guest vNUMA topology
        +
Host memory binding
        +
Host CPU pinning
```

셋 중 하나만 맞고 나머지가 틀리면 NUMA 정렬은 완성되지 않는다.

---

# 9. 잘못된 NUMA 배치에서 발생하는 대표적인 문제

## 9.1 vCPU와 메모리가 다른 노드에 배치됨

```
vCPU → pNUMA 0
RAM  → pNUMA 1
```

가장 전형적인 원격 메모리 접근 문제다.

---

## 9.2 하나의 vNUMA 노드가 여러 pNUMA 노드에 걸쳐 있음

```
Guest vNUMA 0
 ├─ 일부 메모리 → pNUMA 0
 └─ 일부 메모리 → pNUMA 1
```

게스트는 하나의 로컬 노드라고 생각하지만 실제 메모리는 여러 물리 노드에 흩어져 있다.

이 경우 게스트 운영체제가 수행하는 NUMA 최적화가 실제 하드웨어 배치와 일치하지 않는다.

---

## 9.3 vCPU가 여러 소켓 사이를 계속 이동함

CPU pinning이 없다면 Linux 스케줄러는 QEMU vCPU 스레드를 다른 코어로 이동시킬 수 있다.

일반적인 워크로드에서는 이것이 자원 활용도를 높이지만, latency-sensitive 워크로드에서는 캐시 locality와 메모리 locality를 동시에 잃을 수 있다.

---

## 9.4 CPU와 메모리는 맞지만 I/O 장치가 멀리 있음

SR-IOV나 VFIO passthrough 환경에서는 장치가 연결된 PCIe root complex의 위치도 중요하다.

```
vCPU + Memory → NUMA 0
NIC / GPU     → NUMA 1
```

네트워크 패킷이나 GPU DMA가 다른 NUMA 노드의 메모리를 반복해서 접근하면 소켓 간 트래픽이 증가할 수 있다.

따라서 고성능 네트워크와 GPU 워크로드에서는 다음을 함께 정렬해야 한다.

```
CPU
Memory
NIC / GPU
IRQ
Application Thread
```

---

# 10. AWS Nitro는 NUMA를 없애는가

AWS Nitro System은 전통적인 하이퍼바이저 구조에서 수행하던 많은 I/O와 관리 기능을 전용 하드웨어로 분리한다.

AWS에 따르면 Nitro System은 다음 세 요소로 구성된다.

- Nitro Cards

- Nitro Security Chip

- Nitro Hypervisor

Nitro Cards는 VPC 네트워킹, EBS와 로컬 스토리지 같은 I/O 기능을 전담한다. 메인 시스템 보드에는 Intel, AMD 또는 Graviton CPU와 메모리가 존재하며 고객 워크로드가 실행된다. Nitro는 많은 가상화 기능을 전용 카드로 offload하여 호스트 CPU가 고객 워크로드에 더 집중하도록 설계됐다.

> 그림 4. AWS Nitro System 아키텍처

AWS 공식 Nitro 아키텍처 그림 열기

그러나 Nitro가 NUMA 자체를 제거하는 것은 아니다.

물리 호스트가 다중 소켓 또는 다중 NUMA 구조라면 CPU와 메모리 사이에는 여전히 물리적 거리가 존재한다. Nitro의 목적은 가상화 I/O 경로와 관리 기능을 경량화하고 분리하는 것이지, DRAM과 CPU 사이의 전기적·물리적 거리를 동일하게 만드는 것이 아니다.

다만 일반 EC2 사용자는 호스트의 전체 pNUMA 배치 정책을 직접 제어하지 못한다. 사용자는 인스턴스 내부에 노출된 CPU와 NUMA 토폴로지를 기준으로 최적화하고, 실제 호스트 배치는 AWS의 인프라 스케줄러와 Nitro 계층이 관리한다.

따라서 클라우드에서의 NUMA 최적화는 온프레미스 KVM보다 제어 범위가 제한된다.

```
온프레미스 KVM
vCPU pinning, memory bind, PCI locality까지 직접 제어

일반 EC2
게스트에 노출된 topology 범위 안에서 최적화
```

Nitro Enclaves에서도 CPU와 메모리 locality의 개념을 확인할 수 있다. Enclave는 부모 인스턴스의 vCPU와 메모리 일부를 격리해 별도의 제한된 VM으로 구성한다. AWS는 Nitro Hypervisor가 enclave에 할당된 vCPU와 메모리를 부모 인스턴스로부터 격리한다고 설명한다.

---

# 11. Kubernetes까지 올라가도 NUMA는 사라지지 않는다

Kubernetes를 VM 위에 설치하면 계층이 하나 더 추가된다.

```
Pod / Container
       ↓
Guest Linux
       ↓
vNUMA
       ↓
Hypervisor
       ↓
pNUMA
       ↓
Physical CPU / DRAM
```

일반적인 Pod에서는 CPU와 메모리가 여러 코어와 NUMA 노드에 걸쳐 배치돼도 큰 문제가 없을 수 있다.

그러나 다음 워크로드는 topology에 민감하다.

- DPDK와 네트워크 패킷 처리

- SR-IOV

- GPU와 AI 추론

- 고성능 데이터베이스

- 실시간 처리

- HPC

- 낮은 tail latency가 필요한 서비스

Kubernetes의 Topology Manager는 CPU Manager, Device Manager, Memory Manager와 같은 kubelet 구성 요소의 topology 정보를 조정한다. CPU와 장치가 서로 다른 NUMA 노드에서 할당되면 다중 소켓 시스템에서 추가 지연이 발생할 수 있기 때문이다.

> 그림 5. Kubernetes Topology Manager의 Hint Provider 흐름

Kubernetes 공식 Topology Manager 그림 열기

Topology Manager는 다음 정책을 제공한다.

```
none
best-effort
restricted
single-numa-node
```

single-numa-node 정책은 가능한 경우 CPU, 메모리와 장치를 하나의 NUMA 노드에 정렬하고, 하나의 NUMA 노드로 요청을 만족할 수 없으면 Pod admission을 거부한다.

Memory Manager는 Topology Manager에 NUMA affinity hint를 제공하고, Linux에서는 cpuset.mems를 통해 Pod가 사용할 NUMA 메모리 노드를 제한할 수 있다. Guaranteed QoS Pod에 대해 Static 정책을 사용하면 요청 메모리를 최소한의 NUMA 노드에서 확보하려고 한다.

여기서 중요한 함정이 있다.

> Kubernetes는 자신이 실행되는 게스트 운영체제가 보여주는 NUMA 토폴로지만 볼 수 있다.

VM의 vNUMA가 실제 pNUMA와 잘못 매핑되어 있다면 Kubernetes는 잘못된 지도 위에서 CPU, 메모리와 장치를 정렬하게 된다.

이는 공식 문서의 직접적인 표현이라기보다 각 계층의 동작을 연결한 추론이다. 즉, Kubernetes Topology Manager가 Pod를 하나의 vNUMA 노드에 잘 정렬하더라도 그 vNUMA가 호스트의 여러 pNUMA 노드에 흩어져 있다면 물리적 원격 접근은 남을 수 있다.

# 12. 실제 환경에서 NUMA 상태를 확인하는 방법

## 호스트 NUMA 토폴로지

```
lscpu
lscpu -e=CPU,NODE,SOCKET,CORE
numactl --hardware
```

예시:

```
available: 2 nodes (0-1)

node 0 cpus: 0 1 2 3 4 5 6 7
node 0 size: 65536 MB

node 1 cpus: 8 9 10 11 12 13 14 15
node 1 size: 65536 MB
```

NUMA distance도 확인할 수 있다.

```
node distances:
node   0   1
  0:  10  21
  1:  21  10
```

일반적으로 자기 자신에 대한 거리가 가장 작고 다른 노드에 대한 거리가 더 크게 나타난다. QEMU에서도 게스트에 노출할 NUMA distance에서 자기 노드의 거리를 10으로 사용한다.

## 프로세스별 메모리 배치

```
numastat -p "$(pgrep -n qemu-system)"
```

또는:

```
cat /proc/<QEMU_PID>/numa_maps
```

이를 통해 QEMU 프로세스의 페이지가 어느 NUMA 노드에 분포하는지 확인할 수 있다.

## libvirt 확인

```
virsh vcpuinfo <vm-name>
virsh vcpupin <vm-name>
virsh numatune <vm-name>
virsh dumpxml <vm-name>
```

## 게스트 내부 확인

```
lscpu
numactl --hardware
numastat
```

호스트와 게스트의 결과를 나란히 비교해야 한다.

```
Guest vNUMA 0  → Host pNUMA 0
Guest vNUMA 1  → Host pNUMA 1
```

게스트에서 NUMA 노드가 두 개 보인다는 사실만으로는 올바르게 배치되었다고 판단할 수 없다.

# 13. NUMA-aware VM 설계 원칙

## 원칙 1. 가능하다면 VM을 하나의 pNUMA 노드 안에 넣는다

VM 크기가 작고 하나의 물리 NUMA 노드에 들어갈 수 있다면 가장 단순하고 예측 가능한 배치다.

```
VM vCPU + VM RAM
        ↓
Single pNUMA Node
```

---

## 원칙 2. 큰 VM에는 현실적인 vNUMA를 노출한다

VM이 여러 pNUMA 노드를 사용해야 한다면 게스트에게도 여러 vNUMA 노드를 제공한다.

다만 가상 소켓 수를 무작정 늘리는 것이 아니라 실제 호스트의 NUMA 용량과 게스트 운영체제의 topology 인식을 고려해야 한다.

---

## 원칙 3. CPU pinning과 memory binding을 함께 적용한다

```
vCPU pinning만 적용
→ 메모리가 다른 노드에 있으면 원격 접근 발생

memory binding만 적용
→ vCPU가 다른 노드에서 실행되면 원격 접근 발생
```

두 설정은 분리된 기능이지만 운영에서는 한 세트로 취급해야 한다.

---

## 원칙 4. I/O 장치의 NUMA locality까지 확인한다

VFIO, SR-IOV, 고속 NIC와 GPU를 사용하는 경우 PCIe 장치가 어느 NUMA 노드에 연결됐는지 확인해야 한다.

```
cat /sys/bus/pci/devices/0000:XX:YY.Z/numa_node
```

CPU, 메모리와 장치가 같은 노드에 가까울수록 소켓 간 DMA와 인터커넥트 트래픽을 줄일 수 있다.

---

## 원칙 5. HugePages를 NUMA 정렬의 대체재로 생각하지 않는다

HugePages는 TLB miss와 페이지 관리 비용을 줄이는 데 도움이 될 수 있지만 CPU와 메모리가 다른 NUMA 노드에 배치되는 문제를 자동으로 해결하지 않는다.

HugePages도 어느 NUMA 노드에 예약하고 할당됐는지 확인해야 한다.

libvirt는 NUMA 노드별 hugepage 구성을 지원하며, QEMU memory backend도 preallocation과 NUMA binding을 제공한다.

---

# 14. 가상화의 발전은 NUMA를 제거한 것이 아니라 관리 계층을 늘렸다

기술의 흐름을 다시 정리해보자.

```
단일 CPU와 공유 메모리
        ↓
멀티코어·멀티소켓 확장
        ↓
공유 메모리 버스의 확장 한계
        ↓
NUMA
Intel UPI / AMD Infinity Fabric
        ↓
하이퍼바이저
QEMU + KVM / VMware
        ↓
물리 NUMA를 VM에 직접 노출할 수 없음
        ↓
vNUMA
        ↓
CPU pinning + Memory binding
        ↓
AWS Nitro와 클라우드 가상화
        ↓
Kubernetes Topology Manager
        ↓
Pod 단위 CPU·메모리·장치 정렬
```

가상화 기술이 발전할수록 사용자는 물리 하드웨어를 덜 의식하게 됐다.

그러나 성능 엔지니어링 관점에서는 반대다. 계층이 많아질수록 각 계층의 topology가 어떻게 매핑되는지 더 정확히 이해해야 한다.

```
Application Thread
        ↓
Container CPU
        ↓
Guest vCPU
        ↓
QEMU vCPU Thread
        ↓
Host Logical CPU
        ↓
Physical Core
        ↓
Memory Controller
        ↓
DIMM
```

이 연결 중 하나라도 어긋나면 애플리케이션은 정상 실행되면서도 예상보다 느릴 수 있다.

# 결론

NUMA는 단순히 "가까운 메모리는 빠르고 먼 메모리는 느리다"는 하드웨어 개념에 그치지 않는다.

가상화 환경에서는 다음 세 개의 문제로 확장된다.

1. 게스트에 어떤 vNUMA 토폴로지를 보여줄 것인가

1. vCPU를 어느 물리 CPU에서 실행할 것인가

1. 게스트 메모리를 어느 물리 NUMA 노드에 할당할 것인가

여기에 SR-IOV, GPU, AWS Nitro와 Kubernetes가 추가되면 장치 locality와 Pod resource alignment까지 고려해야 한다.

따라서 NUMA-aware 가상화의 핵심은 특정 옵션 하나가 아니다.

> CPU, 메모리, 장치와 소프트웨어 스레드가 실제 하드웨어 topology를 따라 일관되게 정렬되도록 만드는 것이다.

가상화는 물리 서버를 논리적인 자원으로 바꿔준다.

하지만 가장 높은 성능과 예측 가능한 latency가 필요한 순간에는, 그 논리적 자원 아래에 존재하는 물리적 거리를 다시 살펴봐야 한다.
